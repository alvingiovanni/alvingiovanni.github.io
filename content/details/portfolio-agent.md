## Context

Most portfolios are read once, quickly, by someone with a specific question they cannot ask. And a portfolio drifts in the same way a company's reporting does: a number gets updated in one place and not another, a skill list grows without evidence attached, a case study says "validated" without saying against what.

I had built the professional version of the fix at Mindvalley: a [self-serve analytical layer](/#/ai-data-intelligence) with generated insights and a conversational agent over governed data. This site is the same pattern at portfolio scale, and the site itself is the demonstration.

## My role

Everything here is mine: the content model, the semantic layer, the validation, the Worker, and the interface. It is a small system, which is the point. The design choices are the same ones I would argue for at work, made where anyone can inspect them.

## Approach

**A metric layer, not a style guide.** Every headline number is defined once in `content/semantic.json` with a value, a label, a period, and the study it belongs to. Node files reference it as `{{metric:id}}`; the site substitutes at render time and the build script substitutes when generating the static pages. A number cannot drift between a hero and its body because there is only one of it.

**Edges as evidence.** The layer maps each case study to the skills and tools it used. From that one mapping the site renders "Skills used" chips on every study, an "Applied in" list on every skill, and a lens control that dims the map to a theme. A skill node with nothing applied in it stays an honest empty dot.

**Validation in the build.** The script that regenerates the site fails the deploy on drift: a metric defined but never used, a reference to a metric that does not exist, a study with no skills, an edge to a node that is not there. The same discipline that keeps a company's KPI definitions honest, applied to a personal site.

**A cached corpus instead of retrieval.** The agent runs on a Cloudflare Worker that holds the API key and sends the entire corpus, every node and every full case study, as a cached system prompt. At this scale, a few tens of thousands of tokens, that is cheaper, simpler, and more accurate than a vector database: nothing can be missed by a retrieval step because nothing is retrieved. The corpus is generated by the build, so the agent is never behind the site.

**Grounding rules.** The agent answers only from the corpus, cites the node it drew on as a link, never invents a number, and says "not covered here" when the work does not cover a question. One mode, one tone: a research assistant over a body of work, not a pitch.

**Cost controls, in layers.** A per-reader limit, a daily cap, short answers, and a spend limit at the account as the backstop. A question costs a fraction of a cent; the worst month is bounded before it can happen.

**The feedback loop.** Questions are logged (never the reader) so I can see what people actually ask and improve the content where the agent had to say "not covered". It is the same loop the professional version runs on.

## Decision made

The site stopped being a brochure and became a small analytical product: measured, validated, and queryable. The write-up of building it is a case study because the design choices are the work.

## Impact

- One definition per headline number, referenced from every place it appears
- Every study lists the skills it used and every skill links to the work it was applied in
- A grounded, cited answer to a reader's question for a fraction of a cent, with the worst-case monthly cost capped in advance

## What I'd do differently

Nothing structural yet; it is new. The thing I am watching is the question log. If readers ask about things the content does not cover, the right response is to write the content, not to loosen the grounding rules.
